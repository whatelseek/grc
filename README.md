# GRC: оценка влияния и аудит мер защиты

Веб-приложение для двух связанных задач консалтингового проекта:

- **BIA / AIA** — опросник владельца системы вместо Excel-файла: насколько критична
  система и как быстро её нужно восстанавливать. Критичность, MTPD, RTO и RPO считаются
  на лету по логике листа «Расчет».
- **Аудит по CIS Controls v8.1.2** — оценка 153 мер защиты предприятия по 18 контролям,
  с целевой Implementation Group, доказательствами и планом устранения.

Вместе они смыкаются: расчётный RTO говорит, за какое время систему нужно поднять, а
контроли 11 (Data Recovery) и 17 (Incident Response) показывают, чем этот срок
обеспечен. Всё хранится в PostgreSQL и разделено по клиентам: пользователь работает
только с теми клиентами, которые ему назначены.

## Быстрый старт

```bash
cp .env.example .env         # задайте JWT_SECRET и пароль администратора
docker compose up --build
```

- UI: http://localhost:8080
- API и документация OpenAPI: http://localhost:8080/api/docs
- Администратор создаётся при первом запуске из `ADMIN_EMAIL` / `ADMIN_PASSWORD`.

Демо-данные (два клиента, четыре системы, консультант и владелец системы):

```bash
docker compose exec backend python -m app.cli demo
```

## Что умеет

- **Клиенты и системы.** Консультант заводит клиента, его системы и опросник по каждой
  системе; на стартовой странице — выбор клиента.
- **Опросник.** Все 80 вопросов исходного файла: части 1–2 (о системе), части 3–4
  (матрицы «поставьте Х» по четырём типам ущерба и семи срокам), часть 5 (мнение о
  MTPD/RTO/RPO), часть 6 (текущие возможности ИТ). Описания уровней ущерба раскрываются
  прямо над матрицей, для операционного ущерба — по каждой функциональной области.
- **Автосохранение.** Ответы уходят на сервер через ~0,7 с после правки; справа
  показываются прогресс, замечания и пересчитанные метрики.
- **Проверки из столбца «Проверка».** Незаполненные обязательные вопросы и ⚠ на случай,
  когда на более длинном сроке простоя выбран более мягкий уровень ущерба.
- **Расчёт.** Критичность по каждому типу ущерба отдельно для недоступности и потери
  данных, общая критичность, MTPD, RTO и RPO в часах.
- **Сводка.** Таблица по всем доступным системам с фильтром по клиенту, сортировкой и
  выгрузкой в CSV (разделитель `;`, BOM — открывается в Excel без настроек).
- **Аналитика портфеля.** Профиль критичности, ход сбора, разрыв между расчётными
  RTO/RPO и текущими возможностями ИТ (вопросы 79–80) и разбор по типам ущерба.
  У каждого графика есть табличный вид, подписи и подсказки по наведению.

## Требования, версии и историчность

Каталог требований хранится в базе, а не в файле, и живёт версиями.

- **Опубликованная версия неизменна.** Оценка закрепляется за той версией, по которой
  проводилась, поэтому правка требований сегодня не меняет результат прошлого квартала.
- **Чтобы поправить требования,** администратор создаёт черновик на основе любой версии
  (страница «Требования»), меняет формулировки, добавляет свои требования и контроли,
  затем публикует. Новые оценки идут уже по новой версии.
- **Свои требования** помечаются отдельно: видно, что пришло из CIS, а что добавила
  компания.
- **Перенос оценки** на другую версию — явное действие. Вердикты по требованиям,
  которых в новой версии нет, удаляются, но остаются в истории.
- **История изменений** ведётся по каждому требованию: кто, когда и с какого на какое
  значение поменял статус, ответственного, срок, приоритет или комментарий. Видна прямо
  на требовании в оценке.
- **Сравнение двух аудитов** одного клиента: изменение реализации в процентных пунктах,
  готовность по IG1/IG2/IG3, списки «стало лучше» и «стало хуже». Требования, которые
  есть только в одной из версий каталога, показаны отдельно и в сравнение не идут.

## Аудит по CIS Controls

- **Каталог.** 18 контролей и 153 меры защиты из официальной книги CIS Controls v8.1.2,
  с классом актива, функцией NIST CSF 2.0 и принадлежностью к IG1/IG2/IG3.
- **Оценка.** Создаётся на клиента, с целевой группой (IG1 — базовая кибергигиена,
  IG2, IG3). Меры выше целевой группы в объём не входят.
- **Статусы.** Не внедрено / Частично / Внедрено / Не применимо. «Частично» даёт
  половину балла; «Не применимо» исключается из расчёта с обеих сторон, поэтому
  пометить меру неприменимой нельзя, чтобы улучшить процент.
- **Доказательства.** К каждой мере можно приложить файлы (PDF, изображения, документы
  Office, CSV, TXT, JSON, ZIP; по умолчанию до 25 МБ). Файлы лежат на томе
  `EVIDENCE_DIR`, в базе хранится только метаинформация.
- **План устранения.** Невыполненные меры с ответственным, сроком и приоритетом;
  сортировка по группе и приоритету (сначала IG1), отметка просроченных, выгрузка в CSV.
- **Отчёт клиенту** — кнопка «Скачать отчёт» отдаёт .docx: итог и готовность по группам,
  динамика с прошлым аудитом (включая перечень откатов назад), реализация по контролям и
  функциям, план устранения, связь с разрывами RTO из BIA и приложение со всеми
  вердиктами. Формат выбран редактируемый: консультант правит формулировки перед
  отправкой. PDF при необходимости делается из него одной командой
  (`soffice --headless --convert-to pdf`).

Каталог генерируется из исходной книги:

```bash
python scripts/extract_cis_controls.py путь/к/CIS_Controls.xlsx \
    backend/app/data/cis_v8.1.2.json
```

Номера мер в книге хранятся числами, поэтому 3.10 и 3.1 — одно и то же значение ячейки.
Скрипт восстанавливает номер по позиции меры внутри контроля и сверяется с ячейкой: без
этого пять мер (3.10, 4.10, 8.10, 13.10, 16.10) молча затирают своих соседей.

## Роли

| Роль | Что доступно |
| --- | --- |
| `admin` | всё, включая создание пользователей и выдачу доступа к клиентам |
| `consultant` | назначенные клиенты: системы, опросники, приёмка, сводка |
| `respondent` | только опросники, назначенные лично ему |

Аудит создают и завершают администратор и консультант; завершённая оценка закрыта для
правок, пока её не вернут в работу.

Доступ к клиенту выдаёт администратор на странице «Пользователи». Консультант, создавший
клиента, автоматически получает к нему доступ.

Статусы опросника: `draft` → `submitted` (отправить может заполняющий, когда закрыты все
72 обязательных вопроса) → `reviewed` (принимает консультант; после приёмки правки
закрыты, вернуть в работу можно кнопкой «Вернуть в работу»).

## Как считается критичность

Логика перенесена с листа «Расчет» (`backend/app/scoring.py`):

1. Уровни ущерба переводятся в баллы: Низкий 25%, Средний 50%, Высокий 75%,
   Крайне высокий 100%.
2. Балл умножается на вес срока (0.30, 0.25, 0.20, 0.12, 0.07, 0.04, 0.02 — сумма 1.0).
3. Критичность по недоступности (часть 3) и по потере данных (часть 4) — сумма
   взвешенных баллов по всем срокам, отдельно для каждого из четырёх типов ущерба.
4. Общая критичность — максимум из восьми полученных значений.
5. **MTPD** — наименьший срок простоя, на котором достигнут уровень «Крайне высокий».
   Если такого уровня нет нигде, в интерфейсе показывается «вне шкалы».
6. **RTO** — минимум из трёх величин: наименьший срок с уровнем «Средний», половина
   наименьшего срока с уровнем «Высокий», треть наименьшего срока с «Крайне высокий».
7. **RPO** — то же правило по срокам потери данных из части 4.

Расхождение с исходным файлом: на листе «Расчет» шестой срок недоступности подписан
«7 сут» (168 ч), тогда как в опроснике тот же вопрос № 25 спрашивает про 2 недели.
Здесь используется срок из опросника — 336 ч; веса не меняются. Если правильным считается
значение из «Расчета», поправьте `AVAILABILITY_PERIODS` в `scripts/extract_questionnaire.py`
и перегенерируйте шаблон.

## Шаблон опросника

Тексты вопросов, подсказки, выпадающие списки и описания уровней ущерба лежат в
`backend/app/data/questionnaire_v1.json` и отдаются фронтенду через `GET /api/template`.
Файл сгенерирован из исходной книги:

```bash
python scripts/extract_questionnaire.py путь/к/опроснику.xlsx \
    backend/app/data/questionnaire_v1.json
```

Новая редакция опросника добавляется как `questionnaire_v2.json`; у каждого опросника
хранится своя версия шаблона, поэтому старые ответы продолжают читаться.

## Разработка без Docker

Веб-интерфейс отдаёт nginx из собранного `frontend/dist`. Конфиг `frontend/nginx.host.conf`
слушает порт 8080 и проксирует `/api` на uvicorn. В Docker тот же маршрут описан в
`frontend/nginx.conf`, только upstream там — сервис `backend`.

```bash
# backend
cd backend
pip install -r requirements-dev.txt
export DATABASE_URL=postgresql+psycopg://bia:bia@localhost:5432/bia
python -m app.cli demo
uvicorn app.main:app --reload

# frontend
cd frontend
npm install
npm run build
# root in nginx.host.conf points at /workspace; rewrite it to this checkout
sudo sed "s|root /workspace/frontend/dist;|root $(pwd)/dist;|" nginx.host.conf | sudo tee /etc/nginx/sites-available/bia.conf >/dev/null
sudo ln -sfn /etc/nginx/sites-available/bia.conf /etc/nginx/sites-enabled/bia.conf
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo service nginx reload
```

UI: http://localhost:8080. Пока правите интерфейс, `npm run dev` поднимает Vite на порту 5173
с тем же прокси `/api`.

Тесты (нужна работающая PostgreSQL и база `bia_test`):

```bash
cd backend
createdb bia_test
DATABASE_URL=postgresql+psycopg://bia:bia@localhost:5432/bia_test python -m pytest
```

`npm run typecheck` в `frontend` проверяет типы без сборки.

## Структура

```
backend/app
├── data/questionnaire_v1.json  шаблон опросника (сгенерирован из xlsx)
├── data/cis_v8.1.2.json        каталог CIS Controls (сгенерирован из xlsx)
├── scoring.py                  критичность, MTPD/RTO/RPO
├── validation.py               проверки столбца «Проверка»
├── cis_scoring.py              реализация мер по контролям, группам и функциям
├── catalogue.py                каталог требований в базе: версии, клонирование
├── comparison.py               сравнение двух аудитов
├── migrate.py                  запуск миграций из кода
├── scales.py                   перевод ответов о текущих возможностях в часы
├── evidence.py                 хранение файлов-доказательств
├── report.py                   отчёт по аудиту в .docx
├── models.py                   клиенты, системы, опросники, оценки, меры, доказательства
├── routers/                    auth, users, clients, surveys, template, dashboard,
│                               analytics, assessments, evidence, frameworks
├── migrations/                 Alembic
└── cli.py                      init (схема + администратор) и demo
frontend/src
├── pages/                      вход, клиенты, клиент, опросник, аудит, план
│                               устранения, требования, сравнение аудитов,
│                               аналитика, сводка, пользователи
├── components/                 поле вопроса, матрица ущерба, панель результата
└── lib/                        клиент API, типы, форматирование, контекст авторизации
```

Схема управляется Alembic. Контейнер перед стартом выполняет `python -m app.cli init`:
применяет миграции, загружает каталог требований и создаёт администратора.

```bash
python -m app.cli migrate           # только миграции
python -m app.cli import-framework  # загрузить каталог требований
alembic revision --autogenerate -m "что изменилось"   # после правки моделей
```

База, созданная до появления миграций (через `create_all`), не содержит таблицы
`alembic_version`. Для неё: либо завести заново, либо `alembic stamp head` и вручную
догнать недостающие столбцы — безопаснее первое, пока данных нет.

## Разрыв между «нужно» и «сейчас»

Ответы вопросов 79 и 80 («как быстро восстанавливается сейчас», «за какой период
можно потерять данные сейчас») переводятся в часы по шкалам из листа «Списки»
(`backend/app/scales.py`) и сравниваются с расчётными RTO и RPO. Отставание —
это разница в часах; вариант «более 7 суток» даёт оценку снизу и помечается
отдельно. Система, у которой расчёт не дал объектива (все уровни «Низкий»),
в сравнение не попадает: сравнивать не с чем.

## Что не вошло в первую версию

- Импорт заполненных Excel-файлов и выгрузка опросника обратно в xlsx.
- Аудит в офлайн-превью (`npm run build:demo`) — там доступен только BIA.
- Миграции схемы (Alembic).
- История изменений ответов и комментарии консультанта к ответам.
